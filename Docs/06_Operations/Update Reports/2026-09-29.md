## Automation Readiness

Unattended update automation is not ready. The [Fleet Update Runbook](../Fleet%20Update%20Runbook.md) now records host gates, package-manager exit-code semantics, update-channel separation, owner approval boundaries, and required post-checks.

Before automation work begins:

1. Define a per-device manifest for identity, owner, OS/boot context, access, update command, privilege, recovery, reboot signal, post-checks, and log destination.
2. Establish scheduled, retained, restore-tested guest and appdata backups; confirm mount identity before backup or update writes.
3. Add per-manager test cases for no updates, updates available, command error, partial transaction, missing output utilities, and unwritable destination.
4. Keep package removals, AUR prompts, unknown WinGet versions, drivers/firmware, Docker major changes/pruning, partner-owned workloads, and physical dual-boot reboots behind human approval.
5. Exclude hosts without verified unattended access or rollback (LockBox, Nobara/AtlasOS, and VM200) until those prerequisites are addressed.
6. Keep RustDesk, NPM, media services, game service planning, and the no-public-exposure policy as separate inventory/access decisions. Do not add WAN forwarding as an automation convenience.
