Storage Layout

You established a storage separation that became effectively a hard rule:

Critical persistent data:

* `/mnt/core`

Bulk/non-critical media:

* `/storage`

And specifically:

`/mnt/core`

* configs
* databases
* appdata
* exports
* knowledge systems
* anything required for rebuild/recovery

`/storage`

* movies
* media
* downloads
* bulk assets only

A major architectural decision was:
Never allow services to store their only persistent state on `/storage`.

That means:

* Docker bind mounts for databases/configs should point into `/mnt/core`
* backups/export pipelines should target `/mnt/core`
* `/storage` is treated more like a replaceable warehouse

Current `/mnt/core` Structure

At the last snapshot you showed:

```text
/mnt/core
├── appdata
│   ├── core
│   │   └── npm
│   ├── knowledge
│   │   └── affine
│   └── utilities
```

Directionally this evolved into:

* `core/` → infra-level services
* `knowledge/` → documentation/wiki systems
* `utilities/` → secondary/self-contained tools

This was considered a good direction because it:

* separates concerns
* keeps recovery cleaner
* avoids one giant undifferentiated appdata graveyard

Networking Philosophy

You settled heavily into:

* VPN-first access
* avoid exposing services publicly unless necessary

Important constraint:

* router modifications are limited/unavailable

So the stack design started adapting around:

* WireGuard LXC
* internal-only services
* reverse proxy where useful
* avoiding dependence on advanced router control

Order-of-operations for rebuilds became:

1. Network
2. Storage mounts
3. Core infrastructure
4. Applications

That sequencing became important because previous issues traced back to services starting before dependencies were available.

Docker / Service Strategy

* predictable restart behavior

You were actively rebuilding/reorganizing the Docker VM rather than trying to endlessly salvage older layouts.

General deployment standards that emerged:

* bind mounts into `/mnt/core`
